# Testing

## Purpose

Make sure the test suite actually catches regressions — not just that tests exist and pass. A green test suite that doesn't test the right things is more dangerous than no tests, because it creates false confidence.

## When to Use This Skill

- Writing tests for new features, especially anything touching money, inventory, or user accounts
- Reviewing existing or AI-generated tests for real coverage vs. superficial coverage
- Before merging a PR that changes business logic
- When a bug was just fixed — write a regression test for it before closing the ticket
- As part of `production-readiness` sign-off for critical paths (checkout, payment, search)

## Process

1. **Identify what actually needs testing**: business logic, calculations (pricing, discounts, tax, shipping), state transitions (order status), integrations (payment, email, inventory), and anything that has broken before.
2. **Write tests against behavior, not implementation** — a test should still pass if you refactor the internals without changing what the function does, and should fail if the *behavior* changes even if you didn't touch that specific function.
3. **Cover the edges, not just the happy path**: empty/zero/negative/huge inputs, concurrent access, network failures, partial failures (payment succeeds but inventory update fails).
4. **Use the test pyramid appropriately**: many fast unit tests for logic, fewer integration tests for how pieces connect, a handful of end-to-end tests for critical user journeys (browse → cart → checkout → confirmation).
5. **Mock external services** (payment gateway, email, third-party APIs) at the boundary — don't let tests depend on real network calls or real money movement.
6. **Run the full suite** and check it's actually being executed in CI, not just present in the repo.

## Checklist

### Coverage of What Matters
- [ ] Pricing/discount/tax/shipping calculations have tests for standard cases *and* edge cases (zero-price items, 100% discount, stacked discounts, out-of-stock during checkout)
- [ ] Checkout and payment flows are covered by integration or e2e tests, including failure paths (declined card, expired session, network timeout mid-payment)
- [ ] Authentication and authorization logic is tested, including "should this user be denied" cases, not just "should this user be allowed"
- [ ] Previously fixed bugs have a regression test so they can't silently reappear

### Test Quality
- [ ] Tests assert on outcomes/behavior, not on internal implementation details (e.g., test that `calculateTotal()` returns the right number, not that it calls a specific internal helper)
- [ ] Each test verifies one thing and fails with a clear message about what broke
- [ ] Tests are deterministic — no reliance on real current time, random values, or external network state without mocking/seeding
- [ ] Test names describe the scenario and expected outcome (`applies_free_shipping_over_threshold`, not `test3`)

### Edge Cases
- [ ] Empty states: empty cart, no search results, no orders yet
- [ ] Boundary values: exactly at a discount threshold, exactly at stock = 0
- [ ] Concurrent actions: two users buying the last item in stock at the same time
- [ ] Partial failure: payment succeeds but a downstream step (email, inventory, order record) fails — what happens?
- [ ] Invalid/malformed input at API boundaries

### Test Infrastructure
- [ ] External services (payment processor, email, SMS) are mocked/stubbed in tests, not called for real
- [ ] Test data/fixtures are isolated — tests don't depend on shared mutable state or run order
- [ ] Tests actually run in CI on every PR, and a failing test blocks merge
- [ ] No skipped/disabled tests left in without a tracked reason

## Common Issues in AI-Generated ("Vibe Coded") Tests

- **Implementation-mirroring tests**: tests that were generated by looking at the code and asserting it does exactly what it does — these pass immediately, provide no real safety net, and break the moment you refactor
- **Happy-path-only coverage**: generated tests often cover the obvious success case and skip failure/edge cases entirely, because the prompt or context didn't surface them
- **Over-mocked tests**: mocking so much of the system that the test verifies the mocks were called correctly rather than that the feature actually works
- **Flaky time/randomness**: generated tests using real `Date.now()` or random values without seeding, causing intermittent failures unrelated to real bugs
- **Missing negative tests**: authorization logic tested only for the "allowed" case, never for "should be denied"

## Reporting Format (when reviewing existing tests)

```
## Test Review: <feature/file>

### Gaps found
- <scenario not covered> — <why it matters> — <suggested test>

### Weak tests (pass but don't protect against regressions)
- [file] <test name> — <what it actually checks vs. what it should>

### Solid coverage
- <call out what's genuinely well-tested>
```

## Boundaries

This skill focuses on automated test coverage and quality. For manual, human click-through verification of every feature against real requirements, see `functional-qa`. For the final pre-launch system-wide gate, see `production-readiness`. For load/stress testing under traffic, see `performance-audit`.
